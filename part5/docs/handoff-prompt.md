## Notes on the prompt itself

**A bundle carries what you put in it.** The weaker, true version of the finding
this note originally overstated: the structure and tokens travelled because the
canvas held them, and the project's rules did not travel because nobody typed
them. That is not a missing feature. It is an argument for project rules living
in the repo, where `CLAUDE.md` already keeps them, rather than being retyped into
a dialog each time a design is handed over.

**"Use layout 2a" was typed by hand, not generated.** The canvas would not let
us select a single artboard, so the share is scoped to the whole document and
the choice is carried by that one sentence. Worth knowing: the mechanism that
was supposed to carry the selection did not, and a line of prose did.

**It is a pointer, not a payload.** The prompt contains no markup, no colours
and no sizes — it names a project URL and three files and expects the agent to
fetch them through the `claude_design` MCP server. That is the real difference
from pasting a screenshot: a screenshot is all pixels and no structure, this is
all structure and no pixels. It also means the handoff has a dependency a
screenshot does not — the agent needs that MCP server configured, or it needs
the export.

**Which is why the export matters.** `docs/design-system/exports/` holds the
same document as a self-unpacking bundle, and unpacking it yields exactly the
three files this prompt names:

| Named in the prompt | In the export |
| --- | --- |
| `Grandmas Wisdom App.dc.html` | the 61 KB canvas document — all three artboards as live markup |
| `ios-frame.jsx` | the 16 KB iOS device-frame scaffold (`IOSDevice`, status bar, home indicator) |
| `support.js` | the 69 KB canvas runtime the document loads |

So the build can proceed from the export whether or not the MCP route is
available. That redundancy was not planned; it is a side effect of exporting the
canvas in Phase 3, and it turned out to be the thing that made the handoff
robust.

## Verifying the pointer resolved

The prompt asks for an MCP server this session does not have configured. It did
not matter, for two reasons, both checked rather than assumed:

**The `DesignSync` tool reads the project directly.** `get_project` on
`5b8ef819-…` returns *Grandma's Wisdom mobile app*, `type: PROJECT_TYPE_PROJECT`,
`canEdit: true`. Note the type — it is a plain project, not a design system,
which is why `list_projects` never listed it: that method filters to
design-system projects and the canvas is not one. Addressing it by id works
regardless.

**The export is a byte-faithful copy of the live canvas.** Both artboard sets
were diffed after normalising whitespace. The only difference anywhere in all
three artboards is the bundler rewriting one attribute:

```
live    from="./ios-frame.jsx"
export  from="32c2f99b-635c-46cf-af39-6c3fe4108b63#/ios-frame.jsx"
```

Every colour, size, gap, string and state in 2a is identical between the two. So
the canvas has not moved since the export, and the build can proceed from either.
